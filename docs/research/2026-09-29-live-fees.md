# Live fees from the platforms themselves (2026-09-29)

**Question.** For each platform, where does the platform itself tell an ordinary
logged-out visitor at a given location what its order fees are *right now*? The adapters
return that as `feeHints` from `resolveStore`, and the engine lays it over the catalog
field by field (`resolveSchedule`, packages/engine/src/fees.ts).

**Rules kept.** Only responses the adapter already fetches, plus at most one extra
anonymous request per store lookup. A field is filled only when the platform states it,
never guessed or copied from the catalog. No login, credentials, CAPTCHA or proxy.

**Where it ran.** The developer's Mac on residential broadband in Bengaluru, 08:58–09:40
IST. Places: Koramangala, Bengaluru (560034; 12.9352, 77.6245) and Andheri West, Mumbai
(400053; 19.1364, 72.8296). Transports are the adapters' own (impit `chrome151` for
Blinkit, Node fetch for JioMart, DMart and BigBasket, headless Chromium for Zepto and
Instamart).

## Blinkit

**Request.** `POST https://blinkit.com/v5/carts` with body `{"items":[]}`: the web
client's own `CART_POST` (its bundle: `CART_POST: e => "/v5/carts" + …`, sent with
`qd_sdk_request: true` by its `FETCH_CART`). The location travels as in every Blinkit
call (`lat`/`lon` headers plus the `gr_1_lat`/`gr_1_lon` cookies). HTTP 200, about 13 KB,
no login. It persists nothing: cart id 0, user id 0. The adapter sends it concurrently
with the ETA call, so the store lookup takes no longer (Mumbai end to end through
`try.ts`, store plus one search: 740 ms).

**What it states** (the same in both cities, 09:00–09:05 IST):

- `cart_data.bill_details.flat_delivery_charge_attributes`: `graded_delivery_charge_constructs`
  `[0, 99) → ₹25`, `[99, 1000) → ₹0` (struck-through ₹12), `flat_delivery_charge` 25,
  `free_delivery_mov` 99, assignment tag `mov_99|dc_25_0` (type `control`).
- `page_meta.custom_data.platform_charges_data` lists the charge families with the
  assignment in force: `handling_charge` `mov|hc_2`, `delivery_charge` `mov_99|dc_25_0`,
  and `small_cart_charge`, `night_charge`, `convenience_charge` all `{}`.
- `cart_data.additional_charges[0]` carries the handling tag `mov|hc_2`: charge_id 3,
  ₹2, one variation `{amount 2, mov 0}`, so it is flat.
- `bill_details.surge_charge_v2`: `surge_amount` 0, `source` "no_surge", `type` FLAT,
  `mov` 0, `checkouts_block_mov` 0, `small_cart_fee` 0, `small_cart_mov` 0.

**Cross-check against a real bill.** One extra call put one item in a guest cart (Spring
Onion 250 g, ₹21) at Koramangala. The page's own Bill Details widget: Items total ₹21,
Delivery charge ₹25 (tooltip "₹25 for orders **below** ₹99", "₹0 for orders **above**
₹99"), Handling charge ₹2 ("For proper handling…"), Grand total ₹48. Shipment charges:
id 3 "eco_friendly_packaging_cost" ₹2, id 13 "delivery_charge" ₹25. **No small-cart
line**, although that cart's `surge_charge_v2` carried `small_cart_fee` 15 /
`small_cart_mov` 99. That is store configuration for surges, not a charge.

**Traps the parser avoids** (both in tests):
- `bill_details.free_delivery_mov` one level up is not the threshold: 800 in the empty
  cart, 250 with one item. Only `flat_delivery_charge_attributes` is read.
- The small-cart config inside `surge_charge_v2` is not a charge. "No small-cart fee" is
  read only when the `small_cart_charge` family is `{}` *and* the surge source is
  "no_surge"; anything else leaves the catalog.

**Hints returned:** `{deliveryFee: 25, freeDeliveryAbove: 99, handlingFee: 2, smallCartFee: 0, surgeFee: 0}`.
A positive `surge_amount` with `mov` 0 becomes `surgeFee`, and `checkouts_block_mov` > 0
becomes `minOrder`. Neither was seen live (no rain that morning), so both are unit-tested
on edited fixtures only. A graded delivery table with two paid steps, or a table that
contradicts its own flat fields, gives no delivery hint; the same goes for handling that
varies with cart value.

## JioMart

**Minimum order (already reported, now verified).** `mbv_config[Groceries].min_basket_value`
(99 in all 19 stores seen across 3 cities) is a hard minimum. The cart theme bundle reads
it back from `jio_mbv_details` and, below it, prints "Shop for ₹X more from groceries to
place order".

**Delivery fee (new, 1 extra request).** `GET https://www.jiomart.com/ext/jmshipmentfee/delivery_fee/v1.0/quote?store_code=TM3D`
with `x-application-id: <public storefront id>`, no auth. This is the theme's own call
for its "Shop for ₹F to unlock free delivery on your quick grocery order" strip, cached
by the site per store for 30 min. `result.delivery_fee_list`:

| config_name | shipping_fee | free_shipping_threshold |
|---|---|---|
| SMART_BAZAAR_BASKET (quick grocery; `store_cohort` Default, store_code TM3D) | 30 | 199 |
| JIOMARTLITE | 30 | 399 |
| JIOMART_BASKET, WHATSAPP | 0 | 1 |
| STORE_BASKET_ALCOHOL, STORE_BASKET_FLOWERS | null | null |

The cart's free-delivery card keys on `delivery_charge_config_name ===
"SMART_BAZAAR_BASKET"` and shows "Free Delivery unlocked" once the shortfall is ≤ 0, so
the fee stops *at* ₹199 (the engine's rule). Mumbai TZT7 and TD9R: the same ₹30 below
₹199. **Hints returned:** `{minOrder: 99, deliveryFee: 30, freeDeliveryAbove: 199}`. The
quote must echo the store code it was asked for, and a failure leaves the minimum order
alone.

## Instamart

Already wired, re-checked. After select-location and a reload, the site loads
`GET /api/instamart/checkout/v2/cart?pageType=INSTAMART_HOME` itself; its
`comms.nudgeComms.success.text` is still "<b>FREE DELIVERY</b> on orders above ₹199".
Everything else a guest session loads (select-location, `home/v2` pages 1–2,
`im-footer`, the empty cart) states no delivery amount and no handling, small-cart or
surge fee. The same cart now also carries brand offers under `couponlessOffersComms`
("FLAT 10% OFF on … Arata items worth above ₹499"); the parser only reads the delivery
nudge (a test covers it). The hint is read once per browser session, so it is up to
30 minutes old.

## Zepto: nothing usable

- The only JSON the home page loads for a guest is `get_page` (the adapter already calls
  it): `storeDetailsResponse.raining: false`, `mismatchTriggers.checkMovMismatch: false`,
  and no amount anywhere. Bengaluru and Mumbai alike.
- The fee texts in the page ("Rain Fee In Effect", "Surge Pricing In Effect — Surge fee
  added due to high demand", "Demand is extremely high! Fees have been temporarily
  added…") are templates the cart fills in.
- The cart is `POST bff-gateway.zepto.com/cfs/api/v1/cart/create` (then
  `PUT cfs/api/v1/cart`) with `{storeId, cartProducts, latitude, longitude,
  isLayoutRequired, …}`. The site sends it only once the cart holds an item: opening the
  empty cart (`/?cart=open`) made no call. One signed empty call from a guest session
  passed the CORS preflight, then came back from the edge without CORS headers. That
  was 09:17–09:20, when the coordinator's coverage run was also getting Zepto refusals
  from this IP, so it may just be the burst limit. Either way a priced cart needs a
  product variant id, which a store lookup does not have.

## DMart: nothing usable

The pincode lookup states no fee. The checkout family (`/api/v3/secure/shipmodes/10744`,
slots, checkout) answers **401** without login. The only statements are site-wide CMS
strings on www.dmart.in: "Home Delivery : Flat Rs. 49", "Pick Up Point : Free Delivery",
"Welcome to DMart Ready. Now, you can shop for a minimum order value of ₹" plus a number
filled in per cart, "For orders containing festive products, minimum order value is Rs.
300", and the reward "Enjoy free delivery on this order starting from ₹299". They are
not per store, and FeeHints cannot carry a flat delivery fee with no threshold anyway (a
lone `deliveryFee` needs a Delivery rule with a threshold).

## BigBasket (BB Now): nothing reliable

- The header the adapter already fetches has `ticker_info: {}` and
  `special_notifications: {}`. The bbnow door's `door_config.display_msg` reads "4500+
  essential products. FREE delivery (limited period)", while the same response's door
  UI says "Instant delivery of 7000+ essentials". Stale CMS copy with no threshold, so it
  is not read.
- The guest basket `GET /basketService/get/` answers `{cartInfo: {}, success: true}`. A
  priced basket needs an add plus a read (2+ requests) and a product id.

## Where the catalog looks wrong today

These are logged-out quotes for two points, so they are evidence, not proof.

- **Blinkit.** The catalog has delivery ₹30 below ₹199, handling ≈₹5 and small cart ₹20
  below ₹99. Live it is **₹25 below ₹99, handling ₹2, no small-cart fee**, in both
  cities, and a ₹21 bill confirmed it. The assignment type is "control" (an A/B arm).
- **JioMart.** The catalog has ≈₹30 below ₹400 and no minimum. Live it is **₹30 below
  ₹199 and a ₹99 minimum order** for quick grocery. The ₹399 threshold belongs to the
  `JIOMARTLITE` basket, which is probably where "₹400" came from.
- **Instamart.** The threshold matches (₹199). Handling ≈₹10 and small cart ₹15 could
  not be checked anonymously.
- **BB Now.** The catalog's ₹30 below ₹199 could not be checked. The site's (stale?)
  copy claims "FREE delivery (limited period)"; worth one manual look at a real basket.

## Limitations

- **Cohorts.** Blinkit's fees carry A/B assignment tags keyed to the device (ours is
  random per process), and JioMart's quote resolves a store cohort ("Default"). Accounts,
  memberships and first-order offers are not seen.
- **Boundary.** Blinkit's `required_amount_for_next_discount` (100 on an empty cart, 79
  at ₹21) implies free delivery from ₹100, i.e. strictly above ₹99; the engine's rule
  makes ₹99 itself free. Instamart's "above ₹199" is equally ambiguous at exactly ₹199.
- **Blinkit surge.** Only "no_surge" was observed. Whether an *empty* cart shows a rain
  surge is assumed, not seen. The night and convenience charge families have no FeeHints
  field and are not read.
- **Freshness.** Hints live as long as the store cache: 10 min for Blinkit, 24 h for
  JioMart (the site itself caches its quote for 30 min), one browser session (≤30 min)
  for Instamart.

## Pan-India fixes made in the same pass

- **JioMart.** `delivery-promise` with only a pincode returned *no store at all* for
  Delhi 110017 and Kolkata 700064, which is why coverage showed "not served" in ten
  cities. Quick-commerce stores are matched by polygon (`meta.polygon_id`), and the
  site's location flow sends the point as `x-geolocation:
  {"latitude":"…","longitude":"…"}` (strings) next to `x-location-detail`. With it,
  110017 → grocery store 13586 TL5T ("Delivery in 21 mins") and 700064 → 13822 TM6N
  ("20 mins"). The adapter now always sends the point; store picking was already
  right. In Mumbai the point picks TD9R (10495) where the pincode picked TZT7 (3).
- **BigBasket.** Lucknow 226010 and Bhagalpur 812001 answered the serviceable call with
  HTTP 303 `{"errors":[{"code":4056,"code_str":"SERVE4056","type":"SERVICEABILITY
  ERROR",…}]}` (coverage, ~09:20). The same Lucknow point answered 200 (bbnow "bb2.0")
  at 09:31, and its header listed one BB Now area "Back at 11 AM". A SERVICEABILITY
  ERROR from the serviceable or set-location step now returns null ("not served here
  now") instead of an error.
- **BigBasket scheduled delivery.** Jaipur 302017 has no `bbnow` entry, and `bb-b2c`
  (scheduled BigBasket) is "NA" too, so no BigBasket service reaches that point.
  Elsewhere, scheduled delivery is a different service: entry context 100, its own
  service areas (Lucknow: sa 35013 "1 hrs"), slots and the slotted fee table (₹50 below
  ₹600 …), which has no catalog entry. Supporting it means a second entry context in
  `locate()`/search plus a catalog schedule (an engine change). Not built.
- **Zepto refusals in coverage.** They began exactly while this task was opening Zepto
  sessions from the same IP (7 sessions, 09:13–09:20), and coverage itself opens a fresh
  session, and so a fresh WAF challenge, per place. A burst limit is the likely cause.
  No adapter change: sharing one session across places would need Zepto to ignore the
  session's location cookies, which is unverified.
